## The correction that shaped the work

Jeff believed the tool already computed a "% chance to be played on curve". It
did not, and this is worth remembering because the misconception is reasonable:
`ANALYSIS` computes Karsten's *threshold* — `required(pips,turn)` says how many
sources you need, `sourcesFor()` says how many you have, the UI reports the
shortfall. That is a deck-level verdict, it is not a probability, and it cannot
move as you draw.

The probability had to be defined from scratch. `required()` did not become dead
weight — it became the calibration target.

## The math, and the trap

```
P(on curve) = P(hold the card) × P(enough lands) × P(colours | lands)
```

The third factor is the whole problem. Multiplying an *unconditional* colour
probability by the land probability double-counts the land requirement and
understates badly — this is the same trap MEMORY.md's standing facts already
warn about for the deck-level table. So the joint is computed exactly and divided
back out:

```
P(colours | lands) = P(sources AND lands) / P(lands)
```

`P(sources AND lands)` is an exact multivariate hypergeometric over a **disjoint
three-way partition** of the library — lands producing the colour, other lands,
everything else. Disjointness is the trick that makes it tractable: duals and
taplands fall into exactly one bucket, so the overlapping-category problem that
pushed Karsten to Monte Carlo never arises. It is a double sum, O(draws²), about
170 terms at turn seven. Cheap.

Colours are combined by multiplying their conditional factors, which assumes
independence between colours. Exact for a single-coloured requirement,
approximate for a gold card — and the *same* approximation the rest of the tool
already makes, since `required()` is a per-colour table.

## The cross-validation, which is the best evidence in the project

Feeding the `DERIVED` table's own prescribed source counts back through the new
closed form returns **0.88–0.94 castability, essentially flat** across pips 1–3
and turns 1–7:

| | 1 pip | 2 pips | 3 pips |
|---|---|---|---|
| T3 | 0.921 | 0.911 | 0.912 |
| T5 | 0.923 | 0.924 | 0.921 |
| T7 | 0.922 | 0.922 | 0.905 |

`DERIVED` came out of `research/mana-engine` by Monte Carlo and shares no code
with this calculation. Two independent methods agreeing to ~2 points is the
strongest confirmation the mana math has had.

**The flatness matters more than the level.** A model that got the conditioning
wrong drifts steadily with turn number instead of holding level, so flatness is
the specific signature of correct conditioning. There is a test asserting the
spread stays under 0.05.

`KARSTEN` calibrates at or above `DERIVED` in every cell, which independently
confirms the claim already written in `MATH CORE` that the published table is the
more conservative of the two. Also asserted.

## Two real bugs, both in the scorecard, both found by testing

1. **One-land hands kept 79% of the time.** The `early` component scored the
   *earliest turn with a play*, so a hand of one Plains and two one-drops
   collected full marks — 22 of 22 points — regardless of what followed. Casting
   a one-drop and then doing nothing for four turns is a mulligan.

   Replaced with `deployment()`: the probability of having a play on each of
   turns 1–4, **with spells consumed as they are cast**, so two one-drops cannot
   cover four turns. Turns 2 and 3 weighted highest. One-land keeps fell to 4%;
   overall ship rate landed at ~13.5%, which is a believable mulligan rate.

2. **The on-curve mean was weighted by `1/mv`.** A one-drop's land requirement is
   trivially satisfied, so cheap spells scored near 1.0 and — being the heaviest
   weighted — dragged the component up on exactly the hands that deserved it
   least. This was the *second half* of the same bug. Now weighted equally.

Both are pinned by a regression group that asserts keep rates by land count.

## Four test bugs, all mine, all fixed rather than loosened

Worth listing because the house rule is to work out whether the test or the code
is wrong, and this session it was the test four times out of six.

- `JSON.stringify` on a tally object compares **key insertion order**, which a
  shuffle legitimately changes. Sort keys before comparing.
- Hardcoded grid size of 19 where the DERIVED grid is 7+6+5 = 18 rows.
- Compared two seed-picked hands where a **mean over many** was needed — a single
  3-land hand can legitimately score low if its curve has gaps.
- Appended a dead card to an already-60-card fixture and trimmed to 60, silently
  cutting every copy back off the end. Swap a card out, don't append.

And one test that was wrong about the *app*: it spliced an uncastable card into
an already-scored hand and expected the score breakdown to notice. It doesn't,
correctly — the drill view reports the score computed when the hand was dealt,
because the score rates the opening seven and must not drift as you draw. The
card *face* updates live; the breakdown doesn't. Rebuilt the fixture with the
dead card in the deck from the start.

## Architecture notes

- **New `GOLDFISH` banner** between `DIG PAYOFFS` and `RENDER`. This forced the
  one edit outside new code: `tests/extract.js` `SECTIONS` — `payoffs` now ends
  at `GOLDFISH`, and a new `goldfish` slice was added. Miss that and `payoffs`
  silently swallows the entire engine.
- **The view builders live in `GOLDFISH`, not `RENDER`.** `gfBulkHTML` and
  `gfDrillHTML` are pure string builders, so putting them in the testable slice
  means the markup is reachable from node. This matters more than it sounds: the
  failure mode of a template literal is not an exception, it is the word
  `undefined` rendered mid-percentage, and nothing throws. There is an explicit
  regex assertion for `undefined|NaN|[object Object]|Infinity|null%` run across
  every one of 400 rendered hands.
- **`GF` owns its own state and render path.** `render()` never calls
  `renderGoldfish` — it would wipe a drilled-in hand mid-draw on every keystroke.
  `render()`'s single goldfish responsibility is `gfMarkStale()`, which compares a
  signature of the resolved list and flags the panel rather than silently
  redealing. Results are session-only and deliberately absent from
  `snapshotState()`, so a run can never travel in an export or dirty a build.
- **The honest-odds rule is structural, not a comment.** `libraryState()` is built
  by subtracting known cards from the full deck rather than by reading the tail of
  the shuffled order. Same multiset, but it keeps the rule true if someone later
  adds a tutor, a scry, or a bottoming step. A test pins the two routes together.

## Performance

Non-issue. 1000 hands scored twice each in **39ms**; the drill view recomputes
~22 `onCurve` calls per draw. The bulk list caps display at 100 rows with a
"show more", but the statistics always use the full run.

## New modelling gaps, all documented in the Method tab

- Land drops are not sequenced, so a **tapland is treated as producing mana the
  turn it is played**. Optimistic. Fixing it needs a play policy deciding which
  land to lead on, which is a much larger machine.
- A **Verge counts only for its unconditional colour** here — the conditional half
  needs a land in play and cannot be an integer in a hypergeometric partition, so
  it is excluded rather than guessed at. Errs low, consistent with `sourcesFor`.
- Colour independence, as above.
- Hands are scored **as dealt**; no London chain, no auto-bottoming heuristic.
